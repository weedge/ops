# Popto 运营自动化的整体流程

## 一、总体结构

```text
 ┌─ 触发 ────────────────────────────────────────────────────────┐
 │ 定时表 schedules.yaml │ 采集器（TikHub）│ 钉钉群回复 │ CI 轮询 │
 └──────────────┬────────────────────────────────────────────────┘
                ▼ 统一事件 {type, subject, summary, data, dedup_key}
 ┌─ 事件中台 hub（127.0.0.1:8787，hub.db 留底）─────────────────────┐
 │ 去重 → 按 rules.json 第一条命中的规则生成任务                    │
 │ → 同组同时只跑一轮、防抖合并、按优先级排队                        │
 │ 唯一的通知出口：静默时段、每天 10 张卡片上限、待批清单            │
 └──────────────┬────────────────────────────────────────────────┘
                ▼ opsd 长轮询领任务（领到后每 30 秒续一次）
 ┌─ 接单程序 opsd ─────────────────────────────────────────────────┐
 │ 拼 input.md（Skill、相关决定、数据，外部内容放进隔离区）          │
 │ → 按降级链拉起 Agent：claude.sh → codex.sh → agy.sh → WorkBuddy  │
 │   确定性工作（采集、发布、回复、合并）交给脚本，不用大模型         │
 │ → 按 Schema 校验输出 → 业务数据写入 ops.db                       │
 └──────────────┬────────────────────────────────────────────────┘
                ▼ Agent 的输出，按需要分三路去向
   ├─ 日报 / 摘要 → 钉钉群
   ├─ 决策卡片 C12 → 钉钉群 → 人回复「C12 1」→ 中台发出选项里写好的后续事件
   └─ 后续事件 follow_up_events → 回到中台，继续推进流水线
```

**人只做两件事**：批卡片，偶尔补一句「记下来：…」「需求：…」「已发 pk_xx 链接」（视频号没有链接，只回「已发 pk_xx」）。其余环节都由事件推着自动往下走。

## 二、一个任务的生命周期

1. **事件进入中台**：按 `dedup_key` 去重，命中规则后生成任务。同组里如果已有一轮在跑，新任务就排在后面，或在防抖时间内合并成一次。
2. **opsd 领任务**：选第一个可用的 Agent。熔断中的 Agent 会跳过；如果是审查任务，会排除写这份东西的 Agent。
3. **运行**：工具权限按规则的档位给（只读 / 工作区 / 浏览器 / 开发），超时会把整个进程组杀掉。
4. **出错时的处理**：

   | 出错情况 | 处理 |
   | --- | --- |
   | 额度或认证错误 | 熔断这个 Agent，任务换下一个 |
   | 超时 | 换下一个；同一 Agent 连续 3 次超时，熔断 30 分钟 |
   | 输出不合格 | 带上校验错误让同一 Agent 重试 1 次，还不行再换 |
   | 决策、开发、审查任务找不到合适的 Agent | 排队等待，不交给能力弱的 Agent |

5. **处理结果**：数据入库，产生后续事件，需要时发卡片或消息。整条链路都可以用 `opsctl task <id>` 查看。

## 三、四条业务流水线

**① 内容流水线**（周五 15:00 开始）

```text
选题策划 → 写脚本 → 合规审查（Codex，不合格打回，最多改 2 轮）
→ 素材制作（批量口播视频）→ 视频质检 → 生成发布包
→ 17:00 发「今晚发布」卡片 → 人批 → 开了自动发布的平台（抖音 / 视频号 / 小红书）由浏览器自动发，其余推给人
→ 自动发布成功直接登记帖子；人发的回复「已发 pk_xx [链接]」→ 登记帖子
```

**② 数据回收**（发布后自动开始）

```text
登记帖子 → 发布后 1 小时 / 24 小时 / 72 小时 / 7 天各拍一次数据快照（每 30 分钟检查一次）
  数据从抖音 / 视频号 / 小红书创作者后台读（复用发布的登录态），抖音读不到时用 TikHub 兜底；
  没有作品 ID 的帖子（视频号没有链接、短链）按「标题 + 发布时间」在后台对上，再补上 ID
  └─ 数据明显异常（高于中位数 3 倍或低于 0.3 倍）→ 单条复盘
每小时采集评论 → 评论分拣（只读，不可信输入）
  ├─ 回复草稿 → 卡片 → 人批 → 回复执行器发出（不带链接和联系方式）
  └─ 需求信号 → 需求池
06:40 导入漏斗数据，08:30 发日报，周一 09:00 出周报和需求 Top 10
```

**③ 需求 → 开发**

```text
需求信号 / 人回复「需求：…」→ 需求挖掘、归并 → 周一 Top 10 卡片 → 人批
→ 写 PRD → 卡片 → 人批 → Claude 在独立 worktree 里开发并提 MR
→ Codex 审查（最多 3 轮）→ 合并闸门（数据库迁移、计费、鉴权、密钥、改动超过 800 行都要人看）
→ 卡片 → 人批 → 合并 → 线上核实（对不上就发 P0 告警）
```

**④ 获客**

```text
14:00 社媒监听（按痛点词、竞品词、品牌词）→ 线索入库 → 卡片
周三 10:00 GEO 检查（Popto 在 AI 搜索答案里的可见度）
拆解热门内容 → 进入下一轮选题
```

另外还有兜底流程：

- 每周日 10:00 清理，删除要卡片批准。
- 系统故障时 Codex 按 P0 做分拣。
- 没有命中任何规则的事件进日报摘要。

## 四、你一天会看到什么

| 时间 | 钉钉群里出现的内容 |
| --- | --- |
| 08:00 | 夜里攒下的卡片（静默时段只发 P0），超过 2 张时合并成一条「待批清单」 |
| 08:30 | 日报：昨日数据、异常、待批事项、Agent 状态 |
| 白天 | 零星卡片：评论回复、需求、MR 合并等，每天最多 10 张 |
| 17:00 | 「今晚发布」卡片，批完后收到发布包 |
| 22:30 以后 | 只发 P0（线上故障、部署对不上） |

卡片到期没人处理，就按卡片上写好的安全选项处理，这个选项不会做任何对外动作。

## 五、怎么看运行情况

- `opsctl status`：中台、Agent 状态和队列。
- `opsctl tasks`：任务列表。
- `opsctl dashboard`：看板，这是一次性生成的静态页面，看新数据要重新生成。
